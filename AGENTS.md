# AGENTS.md

## Project Shape
- Node.js ESM Discord music bot; runtime entrypoint is `src/index.js`, slash-command deploy entrypoint is `src/deploy-commands.js`.
- Commands are auto-loaded from every `src/commands/*.js` file; each command module must export `data` and `execute`.
- Events are auto-loaded from every `src/events/*.js` file; event modules export `name`, `once`, and `execute`.

## Commands
- Install dependencies with `npm ci`; lockfile is `package-lock.json`.
- Start the bot with `npm start`.
- Run development watch mode with `npm run dev`.
- Deploy slash commands with `npm run deploy`; set `DISCORD_GUILD_ID` for guild-scoped testing. Global deployment requires explicit `ALLOW_GLOBAL_COMMAND_DEPLOY=true` and uses `Routes.applicationCommands(process.env.CLIENT_ID)`.
- `npm run check` runs `node --check` across `src/**/*.js` and `src/*.js`; `npm test` runs the repository's Node test suite. There are no repo-defined `lint`, `format`, or `typecheck` scripts.

## Runtime Requirements
- Requires Node `>=22.12.0`.
- `.env` is loaded via `dotenv/config`; required vars are `DISCORD_TOKEN` and `CLIENT_ID`.
- Playback metadata/search shell out to system `yt-dlp`; local playback and playback fallback use `yt-dlp` plus `ffmpeg`/`ffmpeg-static`.
- The ffmpeg binary is resolved by `src/utils/ffmpeg.js` in this order: explicit `FFMPEG_BIN` env → `/usr/bin/ffmpeg` → `/usr/local/bin/ffmpeg` → `ffmpeg` on PATH → bundled `ffmpeg-static`. The chosen binary must be built with `--enable-libopus`; the resolved path is written back to `process.env.FFMPEG_BIN` so `prism-media`/`@discordjs/voice` use the same binary. `src/index.js` imports `dotenv/config` BEFORE any ffmpeg resolution — keep that order so `FFMPEG_BIN` from `.env` is honoured.
- Prefer system ffmpeg (Ubuntu `6.1.1`) over the bundled binary: `ffmpeg-static@5.3.0`'s `b6.1.1` release actually ships a `7.0.2-static` Linux binary (upstream issue `eugeneware/ffmpeg-static#151`), which has been observed to crash with `SIGSEGV` on long Opus streams. Set `FFMPEG_BIN=/usr/bin/ffmpeg` in the deployment env to avoid it.
- With `PLAYER_BACKEND=lavalink`, YouTube playback uses Lavalink and falls back to local `yt-dlp + ffmpeg` when Lavalink cannot load or continue the track. Bilibili is not parsed by a Lavalink Bilibili source: the bot first uses `yt-dlp` and `YTDLP_COOKIE_FILES` to resolve a short-lived `bilivideo.com` audio URL, then asks Lavalink HTTP source to play that direct URL. If Lavalink direct playback fails, the bot falls back to local `yt-dlp + ffmpeg`.
- Cookies are passed to `yt-dlp --cookies` per platform via `cookieArgs(kind)` in `src/utils/shared.js`: Bilibili calls use `YTDLP_BILIBILI_COOKIE_FILES` (falling back to legacy `YTDLP_COOKIE_FILES`), YouTube calls use only `YTDLP_YOUTUBE_COOKIE_FILES` (never the Bilibili files, so login cookies are not leaked across platforms). Each accepts comma-separated paths but uses the first non-empty path. Cookies should be Netscape `cookies.txt` format; Bilibili cookies normally include login fields such as `SESSDATA`, `DedeUserID`, and `bili_jct`.
- Playback diagnostics (Lavalink-to-local fallback, skip-after-error, radio/Lavalink failure, voice recovery failure) go through `sendPlaybackNotice()` in `src/utils/player.js`, which drops the message when the Bot's voice channel has no human members. This keeps 24/7 guilds from posting error chatter into an empty server. It fails open when the voice channel cannot be resolved; plain `sendToChannel()` is still used for user-triggered messages.
- Local playback has a stream-stall watchdog: while playing, the song is treated as a playback error (retry with rewind, then skip with a channel notice) and local processes are cleaned up only when all of these hold for `LOCAL_STREAM_STALL_MS` (default 20s, e.g. platform throttling): ffmpeg has not exited cleanly (`sourceEnded` is false), the downstream `PassThrough` buffer is drained, and no new bytes arrived. ffmpeg usually transcodes a whole song faster than realtime and exits, so watching only ffmpeg output would misjudge every song whose opus output fits in `AUDIO_BUFFER_MB`; the buffered audio keeps playing and the track ends normally via `AudioPlayerStatus.Idle`. Queue-end branches also call `cleanupProcesses()` so stalled `yt-dlp`/`ffmpeg` children are never orphaned. Child cleanup sends SIGTERM and escalates to SIGKILL after two seconds if a process remains stuck in a pipe write.
- The reference deployment uses two localhost-only Docker helpers for YouTube anti-bot/cipher handling: `bgutil-provider` on `127.0.0.1:4416` and `yt-cipher` on `127.0.0.1:8001`. The matching `bgutil-ytdlp-pot-provider` Python plugin must be installed in the same environment as `yt-dlp`, and the plugin version must match the container version. `lavalink/refresh-youtube-pot.sh` posts a fresh token to Lavalink; the systemd timer runs every four hours and Lavalink's `ExecStartPost` performs a best-effort refresh after each JVM restart. Do not expose these helper ports publicly.
- YouTube playback through Lavalink uses OAuth plus a pinned `youtube-plugin` snapshot. `MUSIC` handles metadata/search; `TV` is the first playback-capable OAuth client. Preserve the TV User-Agent and client-version fixes (#233 and #231) until a release contains them. Validate a representative playback sample when upgrading; successful metadata lookup alone does not prove playback works.
- The OAuth refresh token is configured as `YOUTUBE_OAUTH_REFRESH_TOKEN` in a private Lavalink environment file and referenced from `application.yml`; never inline it into committed config. To re-authorise, clear that variable, restart Lavalink with explicit operator permission, and read the pairing code from the `dev.lavalink.youtube.http.YoutubeOauth2Handler` INFO log (`root: WARN` would otherwise swallow it).
- Verifying YouTube clients: use `GET /youtube/stream/{videoId}` against Lavalink rather than bot logs, but note `TV` has no metadata support, so `?withClient=TV` always returns 400 even when playback works. Omit `withClient` to check overall availability, or just play a track. Also note yt-dlp silently ignores unknown `player_client` values (it warns `Skipping unsupported client`, then falls back to defaults), so confirm which client actually served a URL via the `&c=` parameter before concluding a client works.
- Keep `yt-dlp` current. A stale `yt-dlp` makes YouTube serve throttled `ANDROID_VR` direct URLs that return HTTP 403 after roughly 1MB, which surfaces as mid-song "403/Forbidden" playback errors rather than as an obvious extraction failure. Verify with a full `yt-dlp -f 'bestaudio[ext=webm]/bestaudio' -o <file>` download, not with `-g` alone, since URL extraction succeeds even when the byte range is capped.
- pip installations also need the matching `yt-dlp-ejs` solver (`yt-dlp[default]` includes it); Node alone is insufficient. A reference combination is yt-dlp `2026.8.19`, EJS `0.8.0`, and bgutil plugin/container `1.3.2`. Missing EJS can cause signature/n-challenge failures.
- Playback source errors are classified by `playbackErrors.js`, with TV/TVHTML5 failures taking precedence within aggregated YouTube errors. Transient Lavalink failures get one same-backend retry, then local fallback. `PLAYBACK_RECOVERY_TIMEOUT_MS` defaults to a shared 45s startup/recovery budget; confirmed output clears the start deadline and sustained playback resets retry counts. `pendingPlaybackRecovery` waits/searches run outside the guild lock and must be cancelled on stop/skip/replacement. Use server-reported `lastPosition`, not the client's extrapolated `position`, to confirm Lavalink output. Radio exhausted video IDs cool down in `playbackAvailability.js`; only Radio can try at most two conservatively matched alternate uploads.
- On memory-constrained hosts, configure a deployment-specific Lavalink JVM heap cap and consider `MemorySwapMax=0` in a systemd drop-in. Swap pressure can cause websocket ping timeouts and local fallback; these host-specific settings are not part of the application template.
- `src/index.js` sets `globalThis.File = File` from `node:buffer` before importing Discord code; keep this compatibility shim unless the dependency/runtime issue is verified gone.
- Cloud voice STT defaults to `voiceControl.sttAccessMode: everyone` for all existing and future guilds. Every human member in the main music Bot's channel may use all voice commands without role, requester, or consent-list checks; `sttOptOutUserIds` remains the only per-member exclusion. `off` disables STT for the guild. Mode or opt-out changes must invalidate and abort current voice work.
- AI requires an explicit public HTTPS `AI_BASE_URL`; there is no default private relay. Tests use reserved example endpoints and injected requests.

## Playback Architecture Notes
- `src/utils/player.js` owns queue advancement, Lavalink playback, local fallback, and control routing.
- `activeBackend` tracks the actual backend for the current song: `lavalink` after successful Lavalink `player.play()`, `local` after successful Discord audio player `play()`, and `null` after stop/cleanup. Pause/resume/skip/volume/seek controls must route by `activeBackend` or actual player availability, not just by global `PLAYER_BACKEND`.
- Bilibili songs may need their direct `audioUrl` refreshed before playback or restore because Bilibili CDN URLs expire. Use `Bilibili.getVideoInfo()` to refresh `audioUrl` and `audioUrlExpiresAt` when `freshAudioUrl(song)` is missing/stale.
- Keep local fallback functional even when Lavalink is enabled. Do not assume `isLavalinkEnabled()` means local `ffmpegProcess`, `ytdlpProcess`, or `player` can be ignored; fallback may have created them.
- `lavalinkConnectionShim()` is only a Lavalink state shim. Local playback requires a real Discord voice connection from `joinVoiceChannel()`; do not subscribe a local audio player to the shim.

## Data And State
- Playlist/settings persistence is JSON at `data/musicbot.json`, created by `src/models/database.js`.
- In-memory playback queues live in `musicQueue` in `src/utils/player.js`; they are per-guild and are lost on process restart.
- `.gitignore` excludes private environment files, cookies and their backups, runtime data, logs, recordings and database files. Only `.env.example` and `*.env.example` templates may contain public configuration examples. Never commit real guild/user playlist data, credentials or cookies.

## Verification Notes
- Without Discord credentials and a voice channel, `npm start` only verifies startup/login path partially and may connect to the real bot.
- `npm run deploy` requires real credentials and mutates Discord application commands; do not run it as a harmless validation step.
- For safe syntax/import checks, prefer targeted `node --check <file>` or dynamic imports that avoid logging in.
- `npm run check` is the safe whole-project syntax check.
- Safe Bilibili parser verification can use a dynamic import of `Bilibili.getVideoInfo()` after loading `dotenv/config`; this does not log in to Discord.
- Do not run `npm run deploy` or restart a running Bot unless explicitly requested. Verify the exact process working directory before terminating it; multiple Bot installations may be running on the same host.
- After changing playback routing, test or ask the user to test these flows: YouTube pause/resume/skip, Bilibili pause/resume/skip, YouTube -> Bilibili next, and Bilibili -> YouTube next.
